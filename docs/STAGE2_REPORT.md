## 2. Проверка

### 2.1. E2E-тесты

```
✔ seamless handoff: web → mobile → submit
✔ handoff via 6-digit code and access control
✔ B2B minimum: RBAC, audit chain and export
ℹ tests 3
ℹ pass 3
ℹ fail 0
```

Проверено:

- CRR = 100 % для 8 переданных полей, шага, фокуса, каретки и прокрутки;
- `redeem` без step-up → 403 `STEP_UP_REQUIRED`;
- повторный `redeem` по билету → 409 `ALREADY_REDEEMED`;
- повторный `redeem` по коду → 404 `CODE_NOT_FOUND`;
- запись с веба после перехода → 409 `LEASE_HELD`;
- `claim` возвращает управление, версия растёт;
- WS-события `handoff.redeemed`, `draft.submitted`;
- метрики задержек и счетчики.

### 2.2. Доступность

axe-core 4.14 + WebKit, WCAG 2.2 A/AA: **0 нарушений** на пяти экранах. Профиль
доступности (115 %, высокий контраст, reduce motion) переносится из web в mobile
вместе с черновиком. Подробно — `docs/ACCESSIBILITY_AUDIT.md`.

### 2.3. UI-прогон (WebKit)

Сценарий: вход → создание перевода → шаг 2 → QR → мобильный демо-клиент →
Face ID → подхват → редактирование на телефоне → submit. Прогон завершён без
console/page errors. Скриншоты: `docs/screens/01…07.png`.

### 2.4. Метрики (локальный контур, loopback)

| Метрика | Значение | Комментарий |
|---|---|---|
| `syncLatencyMs.p95` | 1 мс | серверная обработка PATCH + публикация |
| `clientSyncLatencyMs.p95` | 1 мс | получение WS-события на другом клиенте (localhost) |
| `redeemLatencyMs.p95` | 1 мс | обработка погашения билета |
| `handoffLatencyMs.p95` | 2 806 мс | время «билет выдан → пользователь подтвердил», включает человека |
| `handoffsRedeemed` | 1 | успешный переход |
| `submissions` | 1 | завершённая операция |
| HTTP PATCH p95 (50 конкурентных клиентов, 1 500 запросов) | 15 мс | локальный контур, `scripts/load-check.mjs`; 0 ошибок, ~7 975 RPS |
| axe-core, WCAG 2.2 AA | 0 нарушений | 5 экранов, включая модальные окна |

Вывод: интерактивный бюджет p95 ≤ 150 мс на loopback выполняется с запасом
(15 мс под нагрузкой 50 конкурентов, 1 мс — серверная обработка);
промышленная проверка требует сети и нагрузки (k6, 50–500 VU). Цифры 2,8 с
относятся к UX-времени, а не к задержке синхронизации.

## 4. Ограничения

1. **Flutter проверен**: `flutter analyze` — 0 ошибок и предупреждений (только
   info об устаревших `withOpacity`), `flutter build web --release` собирается.
   Нативные Android/iOS не собирались: нет Android SDK/CocoaPods; инструкции —
   в `apps/mobile/README.md`.
2. **Redis проверен**: собран из исходников (Redis 7), E2E-тесты 3/3 прошли на
   `redis://127.0.0.1:6399`; API в демо-режиме работает с Redis.
3. **k6 не запускался**: сценарий готов, пороги заданы; нагрузочная проверка
   выполнена Node-скриптом `scripts/load-check.mjs`.
4. **HMAC и HTTP** — только демо; промышленный контур: OIDC/RS256, KMS, TLS, WAF.
5. **Один пользователь** и отсутствие платёжного ядра — сознательное ограничение.
